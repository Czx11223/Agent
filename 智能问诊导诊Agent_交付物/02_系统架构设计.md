## 1. 架构总体说明

### 1.1 架构模式

系统采用 **B/S 前后端分离的浏览器/服务端架构**：

- **浏览器端（前端）**：React SPA，负责对话界面、报告渲染与历史会话管理，通过 HTTP/REST 与 SSE 流式接口与后端通信。
- **服务端（后端）**：FastAPI 提供 RESTful + SSE API，承载用户认证、对话状态管理、追问策略编排、LLM 调用、报告生成与数据存储。
- **大数据语言模型层**：通过 OpenAI 兼容接口接入国内可直连的 LLM，负责追问生成、情绪安抚与报告撰写。
- **关系数据库层**：sqlite3，存储用户、会话、消息、报告与评测等数据。

### 1.2 设计原则

| 原则 | 说明 |
| --- | --- |
| 前后端分离 | 前端不依赖后端渲染，通过标准 API 契约解耦，可独立迭代与扩展 |
| 分层解耦 | 业务逻辑、Agent 编排、大模型调用、数据访问分层独立 |
| 编排可配置 | 追问策略、提示词、症状—科室映射、急重症词表独立配置，便于迭代优化 |
| 流式优先 | 对话采用 SSE 流式输出，降低首响应感知时延 |
| 安全合规 | 全链路 HTTPS、敏感数据加密、越权校验、输出守卫、免责与急重症拦截 |
| 轻量可部署 | 基于 sqlite3，适合 demo 级独立部署与后续扩展为 MySQL 等关系库 |

### 2.1 前端层

| 组件 | 职责 | 技术要点 |
| --- | --- | --- |
| 路由与页面 | 登录/注册、对话、报告详情、评测管理 | React Router |
| 对话组件 | 消息气泡流、输入、流式增量渲染、追问引导 | SSE 客户端 + eventSource 封装 |
| 报告组件 | 结构化预问诊报告、科室推荐卡片、豁免声明 | Markdown 渲染 |
| 认证模块 | 令牌存储/刷新、请求拦截、403 处理 | JWT + axios 拦截器 |
| 状态管理 | 会话上下文、用户态、全局 loading | 轻量本地/全局 Store |
| 响应式 | PC / 移动端适配 | TailwindCSS |

### 2.2 API 网关层（FastAPI）

| 组件 | 职责 |
| --- | --- |
| Auth 中间件 | JWT 签发、校验、刷新；角色与权限校验 |
| 校验层 | Pydantic 请求/响应模型、输入白名单校验 |
| 路由模块 | 用户、会话、消息、报告、评测路由；版本前缀 `/api/v1` |
| SSE 端点 | `/api/v1/chat/stream` 建立长连接流式推送 |
| 横切能力 | 限流、日志埋点、错误码统一封装、异常处理、HTTPS 终止 |

### 2.3 Agent 对话编排层（AgentScope，核心）

本层是实现多轮智能问诊的引擎，包含以下核心控制器：

| 控制器/能力 | 职责 |
| --- | --- |
| ConversationManager | 会话生命周期、上下文记忆窗口、会话串接 |
| SlotFiller（槽位填充） | 从用户句抽取并合并五类要素槽位（症状/部位/时间/伴随/既往） |
| ChaseStrategy（追问策略） | 按"主要症状→部位→持续时间→伴随症状→既往史"追问链推进 |
| CompletenessJudge（完成度判断） | 判定信息是否齐备，决定继续追问或转入报告生成 |
| EmotionRecognizer | 识别焦虑/疼痛等情绪并触发安抚话术 |
| EmergencyTriage | 急重症词表 + LLM 双通道识别，命中即急诊拦截 |
| ReportGenerator | 由齐备槽位驱动 LLM 生成结构化报告 |
| DeptRecommender | 依据症状—科室映射表输出 Top3 推荐及理由 |

**Agent 编排流水线（一次用户消息的处理）：**

```
用户消息
   │
   ▼
① 输入预处理（规范化）
   │
   ▼
② 急重症检查（EmergencyTriage）──命中→ 急诊提示，中止追问
   │ 未命中
   ▼
③ 情绪识别（EmotionRecognizer）──有情绪→ 安抚后继续
   │
   ▼
④ 槽位抽取/更新（SlotFiller）＋指代消解
   │
   ▼
⑤ 完成度判断（CompletenessJudge）
   ├─ 不足 → 生成下一轮追问（LLM）→ SSE 流式回复
   └─ 齐备 → 报告生成（ReportGenerator）→ 科室推荐 → 结案回复
```

### 2.4 大模型服务层（LLM）

| 能力 | 说明 |
| --- | --- |
| 模型接入 | OpenAI 兼容接口，模型 Key/BaseURL 可配置，国内可直连 |
| 流式生成 | Chat Completions `stream=true`，逐 Token 转发给 SSE 客户端 |
| 提示词模板 | 系统人设、追问模板、报告模板、免责边界独立管理 |
| 输出守卫 | 敏感内容过滤、指令注入防范、科室推荐规则校验、越界拒答判别 |

### 2.5 数据持久层

- 采用 sqlite3，WAL 模式提升并发读写。
- 对敏感健康列做应用层加密存储。
- 表结构与字段定义：见《数据库设计文档》。

## 4. 核心接口与协议设计

### 4.1 接口清单（RESTful，前缀 `/api/v1`）

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | /auth/register | 用户注册 |
| POST | /auth/login | 用户登录，返回 JWT |
| POST | /auth/refresh | 刷新访问令牌 |
| GET | /users/me | 当前用户信息 |
| GET | /conversations | 会话列表 |
| POST | /conversations | 新建会话 |
| GET | /conversations/{cid} | 会话详情（含历史消息） |
| DELETE | /conversations/{cid} | 删除会话（软删） |
| GET | /conversations/{cid}/messages | 会话历史消息 |
| POST | /chat/send | 发送单条消息（非流式） |
| POST | /chat/stream | **发送消息并以 SSE 流式返回对话** |
| GET | /reports/{rid} | 报告详情 |
| GET | /reports/{cid} | 会话对应的预问诊报告 |
| POST | /reports/{rid}/export | 导出报告 |
| POST | /evaluation/run | 触发评测跑批 |
| GET | /evaluation/summary | 评测指标统计 |

### 4.2 SSE 流式协议示例

```text
POST /api/v1/chat/stream
Authorization: Bearer <jwt>
Content-Type: application/json
{ "conversation_id": "c-001", "content": "我胸口疼三天了" }

响应（SSE，text/event-stream）：
event: token        data: {"delta": "您好，" }
event: token        data: {"delta": "感谢您的描述。" }
event: slot         data: {"slot": "部位", "value": "胸口"}
event: emergency    data: {"flag": false}
event: question     data: {"text": "请问疼痛持续多长时间了？"}
event: done         data: {"next": "ask_more"}     // 或 {"next":"report_ready"}
```

SSE 事件类型：`token`（增量文本）、`slot`（槽位更新回执）、`question`（完整问句）、`emergency`（急重症标记）、`done`（回合结束，携带下一步状态）。

### 4.3 错误码与响应规范

统一响应结构：`{ "code": 0, "message": "ok", "data": {...} }`。常见错误码：`401` 未认证、`403` 越权、`404` 资源不存在、`429` 限流、`500` 服务异常、`6002` LLM 调用失败等。

## 5. 关键业务流程时序（文本描述）

### 5.1 多轮预问诊主流程

1. 患者登录后在前端点击"开始预问诊"，前端 `POST /conversations` 创建会话，状态 `diagnosing`（问诊中）。
2. 患者输入主诉，前端 `POST /chat/stream` 发起流式交互。
3. API 网关校验 JWT 后转发至 Agent 编排层。
4. Agent 处：急重症检查 → 情绪识别 → 槽位抽取/指代消解 → 完成度判断。
5. 若信息不足：LLM 生成下一轮追问，经 SSE 以 `token/question` 事件流式推送给前端。
6. 若信息齐备：触发报告生成（LLM）→ 症状—科室映射推荐 Top3 → 写入 `pre_diagnose_report` → `done` 事件返回报告标识。
7. 前端跳转报告页，展示结构化报告、科室推荐与免责声明，支持复制/导出。

### 5.2 急重症拦截流程

1. 任一用户消息先通过 EmergencyTriage（词表快速匹配 + LLM 语义校验）。
2. 命中"胸痛、呼吸困难"等急重模式：立即返回 `emergency` 事件，提示"建议立即急诊就医或拨打 120"，**中止本轮及后续追问**。
3. 该回合对话仍写入会话历史，并在报告中标记紧急提示已触发。

### 5.3 认证流程

1. 注册：校验手机号唯一性与密码强度。
2. 登录：校验凭证，签发 access token + refresh token。
3. 敏感接口：API 网关校验 JWT，做角色/本人资源归属校验（越权校验）。
4. 令牌过期：前端拦截 401 并用 refresh token 续期。

### 5.4 评测流程

1. 评测人员上传/选用评测集（≥100 条，含标准答案）。
2. 后端批量执行对话编排，记录每回合槽位与最终报告/科室推荐。
3. 统计关键信息追问覆盖率、报告字段完整率、科室推荐 Top3 准确率、平均响应时间。
4. 保存评测记录与 bad case，供策略与提示词迭代。

## 6. 关键设计权衡与决策记录（ADR）

| 决策点 | 选择 | 备选 | 理由 |
| --- | --- | --- | --- |
| ADR-1 对话输出协议 | SSE 流式 | WebSocket | SSE 单向推送更简单，满足文本流式（无需双向长连接），兼容性好 |
| ADR-2 后端语言 | Python 3.12 + FastAPI | Node/Java | 对齐任务书技术栈，AgentScope 原生化支持 |
| ADR-3 Agent 框架 | AgentScope | 自研状态机 / LangChain | 任务书指定，提供多轮状态与编排能力 |
| ADR-4 数据库 | sqlite3 | MySQL/PostgreSQL | 轻量、零运维，满足 demo；结构设计兼容未来迁移 |
| ADR-5 前端 | React + Tailwind/AntD | Vue | 任务书指定，组件生态齐全 |
| ADR-6 模型接入 | OpenAI 兼容 API | 各家私有 SDK | 解耦模型供应商，便于替换 |
| ADR-7 科室推荐 | 规则映射 + LLM 双重保障 | 纯 LLM | 规则保证可溯源与稳定性，LLM 兜底语义理解，兼顾准确率 |
| ADR-8 敏感信息 | 应用层加密列 | 明文 | 满足合规，最小化数据库泄露风险 |

## 7. 安全性架构

- **传输**：全站 HTTPS，Nginx 终止 TLS。
- **认证授权**：JWT + refresh token，网关统一鉴权，对象级越权校验。
- **LLM Key 隔离**：模型密钥仅存服务端，不向前端暴露。
- **输出/输入守卫**：指令注入检测、敏感内容过滤、免责与越界拒答规则。
- **数据安全**：健康列应用层加密；日志脱敏；隐私协议与删除支持。
- **急重症/免责**：Agent 编排层规则引擎强制执行（RTL-01/02/03）。

## 8. 性能与可扩展性设计

- **降低时延**：SSE 流式首 Token 展示、模型/系统稳定的国内可直连 API、追问与报告调用并行复用上下文。
- **并发**：uvicorn 多 worker + 连接池；sqlite3 WAL 提升写并发。
- **扩展路径**：会话状态与 Agent 编排状态分离可水平扩展；数据库可迁移至 MySQL；SSE 可替换为 WebSocket（ADR-1 预留事件协议）。
